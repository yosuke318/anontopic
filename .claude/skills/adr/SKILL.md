# ADR（設計判断の記録）

## なぜ ADR を書くか

このリポジトリの [CONTRIBUTING.md](../../../CONTRIBUTING.md) は、コードコメントに過去の実装との比較を
書くことを禁じている。コメントは「今のコードが何をするか」だけを説明し、実装が変われば
コメントも変わるからだ。

その結果、**「なぜその設計を選んだか」「何を検討して捨てたか」の行き先がなくなる**。
それを置く場所が ADR。ADR は決定した時点のスナップショットなので、後から実装が変わっても
嘘にならない。

半年後に「なんでこんな作りになってるんだ」と思ったとき、git log は *何が* 変わったかは
教えてくれるが、*なぜ* 他の案を捨てたかは教えてくれない。ADR がその差を埋める。

## ADR を書くべき判断

- **技術選定**: 言語・ミドルウェア・ライブラリ・実行基盤・外部サービスの採用
- **元に戻すのが高くつく決定**: データモデル、テーブル分割、外部に公開する API / イベントの形、
  認証・セッションの方式
- **複数案を比較して片方を捨てた**: 捨てた理由こそが後で必要になる
- **一見不自然な選択**: コスト上限、法規制、個人開発の運用体制など、コードからは見えない
  制約に合わせた判断
- **設計書と実装がずれる決定**: 基本設計書に書かれた前提を、実測や検証の結果として変えたとき

## ADR にしなくてよいもの

- 命名、フォーマット、責務の切り直しなど、コードを読めば分かる範囲の判断
- 基本設計書や Linear の issue に既に書いてあることを、そのまま実装しただけのもの
- 数日で消える一時的な回避策 → コード内の `TODO(YOSUKE-NNN)` と issue で足りる

判断に迷ったら「**半年後の自分がこの選択を見て驚くか**」で決める。驚くなら書く。
ADR が増えすぎて読まれなくなるのは、書かなすぎるのと同じくらい良くない。

## 手順

1. `ls docs/adr` で既存の番号を確認する。`docs/adr` が無ければ作る。
2. 次の連番でファイルを作る: `docs/adr/NNNN-kebab-case-の英語タイトル.md`
   （例: `docs/adr/0003-use-air-for-hot-reload.md`）。番号は 4 桁ゼロ埋め、欠番も再利用もしない。
3. [assets/template.md](assets/template.md) をコピーして埋める。本文は日本語で書く。
4. **その決定を実装する PR に ADR を含める。** 後からまとめて書こうとすると、
   検討して捨てた案を思い出せなくなり、ADR の価値の大半が失われる。
5. 対応する Linear issue（`YOSUKE-NNN`）を必ず本文に書く。

## 各項目の書き方

**タイトル** — 決定を動詞で言い切る。「PostgreSQL のバージョン」ではなく
「PostgreSQL 18 を採用する」。何を決めたのかが一覧で分かる。

**ステータス** — `Proposed`（合意前） / `Accepted`（採用済み） / `Superseded by ADR-NNNN`。
個人開発なので、実装と同時に決まるものは最初から `Accepted` でよい。

**文脈** — 制約を事実として並べる。「予算は月額4万円前後」「開発体制は1名」
「同時接続上限は1,000」のように、判断の前提を後から検証できる形で書く。
ここに願望や感想を混ぜない。

**決定** — 一文で言い切る。条件付きなら条件も書く。

**検討した代替案** — **ADR の中で一番価値がある部分**。案ごとに「なぜ捨てたか」を書く。
「良さそうだが今回は合わない」で終わらせず、どの制約に反したのかを示す。

**影響** — この決定で引き受けたコストと、将来これを見直すべき条件（「負荷試験で
egress が想定を超えたら再検討」など）。見直し条件を書いておくと、次に迷った人が
ゼロから考え直さずに済む。

## 決定を変えるとき

**既存の ADR は書き換えない。** 新しい ADR を書き、古い方のステータスを
`Superseded by ADR-NNNN` に変えて、新しい方の「文脈」に何が変わったのかを書く。

過去の判断の記録を消してしまうと、同じ議論を最初からやり直すことになる。
「一度これを試して駄目だった」という記録自体が資産になる。

## 長さ

1 画面に収める。読まれない ADR は存在しないのと同じ。
