# 負荷試験の結果

同時接続 1,000 で、設計の前提（ADR-0029・ADR-0031）の構成が足りるかを確かめた記録。
試験の道具と手順は [test/load/README.md](../test/load/README.md) にある。

## 2026-10-25: 同時接続 1,000

### 条件

| 項目 | 値 |
| --- | --- |
| 環境 | dev を `load_test = true` で構築（prod と同じ台数・クラス） |
| API | ECS Fargate ARM64、0.25 vCPU / 0.5 GB × 2 タスク |
| RDS | `db.t4g.small`、Single-AZ |
| Redis | `cache.t4g.micro`、1 ノード |
| 配置 | タスク・RDS・Redis・NAT を `ap-northeast-1a` に寄せる（ADR-0039） |
| 経路 | 手元の Mac → インターネット → ALB（HTTPS / WSS） |
| シナリオ | セッション発行 → 2 人ルームでマッチング → WebSocket で 10 分接続 → 退出 |
| 送信 | 1 人 10 秒に 1 通、本文 40 文字（全体で 100 通/秒、配信は 200 件/秒） |
| 開始 | 1 秒に 20 人ずつ、50 秒で 1,000 人 |

クライアントは 1 台（1 つの IP アドレス）なので、IP アドレスごとの接続数とマッチング要求の
上限を外している。全体の上限（1,000）はそのまま。

### クライアント側

| 項目 | 結果 |
| --- | --- |
| セッション・マッチング・接続 | 1,000 人すべて成功、失敗 0 |
| 送信 / 配信 | 59,996 通を送り、相手への配信 59,907 件（差は終了間際に相手が先に退出した分） |
| 配信遅延 | p50 11ms / p90 15ms / p99 31ms / 最大 607ms |
| ハンドシェイク | p50 44ms / p90 52ms / p99 79ms |

遅延は送信者と受信者が同じプロセスにいて、同じ時計で測っている。手元からの往復の時間を含む。

### サーバー側（接続が 1,000 本そろっていた 9 分間、1 分ごとの値）

| リソース | 指標 | 平均 | 最大 |
| --- | --- | --- | --- |
| API（2 タスク） | CPU 使用率 | 14.7% | 34.8%（1 タスクの 1 分値） |
| | メモリ使用率 | 18.1% | 24.0%（約 120 MB / 512 MB） |
| RDS | CPU 使用率 | 7.3% | 8.2% |
| | 接続数 | 6.8 | 8 |
| | 空きメモリ | 1.08 GB | 最小 1.07 GB |
| | 書き込み IOPS | 13.8 | 21.1 |
| Redis | エンジンの CPU 使用率 | 5.8% | 7.4% |
| | 接続数 | 779 | 782 |
| | メモリ使用率 | 6.3% | 6.3% |
| | 送信バイト | 13.4 MB/分 | 15.8 MB/分 |
| ALB | 処理バイト | 3.3 MB/分 | 3.8 MB/分 |
| | 5XX | 0 | 0 |

goroutine の数は測っていない。サーバーに数を外へ出す口が無い。メモリ使用率が 24% で
止まっていることから、接続ごとの goroutine がメモリを圧迫してはいない。

### ハードキャップ

1,100 人を流したところ、同時接続のピークは 1,000 本で、残りの 100 人は WebSocket の
ハンドシェイクで 503 を受けた。相手が入れなかった 24 の部屋は、再接続の猶予（30 秒）の後に
`user_left` で終わった。

### 転送量と費用

ALB の処理バイトは 1 時間あたり約 200 MB（クライアントとの送受信の合計）。1,000 本が
1 か月（730 時間）続いたとしても約 146 GB で、インターネットへの送信はその一部になる。
設計書 5 章は egress を約 $109/月（約 950 GB）と見積もっていたが、この送信間隔では
その 6 分の 1 以下になる。AWS は全サービス合計で月 100 GB までのインターネットへの送信を
無料にしているため、API の送信の費用は月数ドルに収まる。

- この数字は API と WebSocket だけのもの。サイトの HTML や静的ファイル（CloudFront）は含まない。
- 送信間隔を縮めると転送量はそれに比例して増える。1 人 2 秒に 1 通なら約 5 倍になる。
- Redis の送信は 1 時間あたり約 800 MB あるが、タスクと同じ AZ の中の通信なので課金されない
  （ADR-0039）。

ALB の LCU は、接続数（3,000 本/LCU）が最も大きい次元で約 0.33 LCU にとどまる。ADR-0029 は
処理量を 1.3 GB/時として LCU を月約 $8 と見積もっていたが、それを下回る。

dev を動かした分の請求額は、Cost Explorer に翌日以降に反映される。

### 結論

- API の 0.25 vCPU / 0.5 GB × 2 タスクは、1,000 接続で CPU・メモリとも余裕がある。
  ADR-0029 の見直し条件（足りなければ 0.5 vCPU / 1 GB に上げる）には当たらない。
- RDS の `db.t4g.small` は CPU が 8% 前後で、t4g.small のベースライン（20%）を下回る。
  CPU クレジットの追加課金は起きない。
- Redis の `cache.t4g.micro` は CPU・メモリとも 10% 未満。
- インスタンスのサイズと台数は変えない。egress の見積もりは、実際の送信間隔が分かったら
  設計書 5 章を直す。
