# ADR-0013: 同時接続数を Redis の期限付きリースで数え、上限に達したら接続を拒否する

- ステータス: Accepted
- 日付: 2026-09-02
- 関連 issue: YOSUKE-126

## 文脈

同時接続数の上限は 1,000 で、これはアプリケーション層で強制すると決まっている（設計書 2 / 6）。
上限が守れないと、月額 4 万円の予算のうち最大の項目である egress（1,000 接続想定で約 $109）が
そのまま上振れする。

- サーバーは EC2 2 台の固定台数構成で、オートスケーリングは使わない（設計書 5 / 6）。
  接続はどちらの台に来るか分からないため、上限は 2 台を横断して数える必要がある。
- WebSocket 接続はプロセスが持つ。プロセスが異常終了すると、その台が持っていた接続は
  誰も減算しないまま残る。カウンタを INCR / DECR で持つと、この取りこぼしが積み上がって
  実際には空いているのに新規接続を拒否し続ける状態になる。
- 接続数以外に、メッセージの連投とマッチングの連続要求も止める必要がある。どちらも
  1 人が何度も投げるもので、少し間を空ければ再開できるのが望ましい。
- Redis は小型ノード 1〜2 台（設計書 5）。接続 1 本あたりに何往復も掛けられない。

## 決定

同時接続数を Redis のソート済みセットで数える。メンバーは接続ごとのリース ID、スコアは
最後に更新した時刻（ミリ秒）とする。接続は開いている間リースを更新し続け、閉じるときに
自分のメンバーを削除する。上限に達している間は新規接続を拒否し、待機列には入れない。

- 上限判定・登録・件数の読み出しは 1 本の Lua スクリプトで行う。接続 1 本あたり 1 往復で済み、
  2 台が同時に空き 1 を取り合っても上限を超えない。
- 判定の前に、リースの寿命を過ぎたメンバーを `ZREMRANGEBYSCORE` で落とす。異常終了した台の
  接続はこれで数から消えるため、カウンタが減らないまま詰まることがない。
- 拒否は HTTP ハンドシェイクの段階で返す。サービス全体が上限なら 503、IP ハッシュ単位の
  上限なら 429 とし、どちらにも `Retry-After` を付ける。
- メッセージ送信レートとマッチング要求レートは、Redis 上のトークンバケットで制限する。
  メッセージはセッショントークン単位、マッチング要求と接続数の副次的な上限は IP ハッシュ単位。
- 上限値・リースの寿命・各レートは環境変数で変えられる。

## 検討した代替案

### 案A: INCR / DECR のカウンタ 1 個で数える

最も単純で、1 往復で済む。ただし接続ごとの期限を持てないため、プロセスが異常終了すると
その台が持っていた接続ぶんカウンタが減らない。TTL をキー全体に付けると、生きている接続まで
まとめて数から消える。異常終了が予算超過ではなく「誰も繋げない」に化けるため採らない。

### 案B: 上限に達したら待機列に入れる

設計書 6 が拒否と並べて挙げている選択肢。待っている人を Redis に持ち、空きが出た順に通す
必要があり、待機中の接続をどう保持するか（HTTP を掴んだまま待つか、ポーリングさせるか）を
決めることになる。マッチング側にすでに待機キューがあり、そこで待つのと二重になる。
上限に達するのは想定を超えた事態であって定常運用ではないため、実装量に見合わない。

### 案C: 各サーバーが自分の接続数だけを数え、上限を台数で割る

Redis を経由しないので最も速い。ただしロードバランサが偏らせた場合、片方が上限に達して
拒否している横でもう片方が空いている状態になる。固定 2 台構成では偏りを吸収する余地がない。

### 案D: レート制限を固定窓のカウンタで行う

`INCR` と `PEXPIRE` だけで書ける。ただし窓の境目で 2 窓ぶんが一度に通るため、連投防止という
目的に対して穴が残る。トークンバケットとの差は Lua 数行で、その差は引き受ける。

## 影響

- リースの寿命（既定 30 秒）のあいだ、異常終了した台の接続がリースを持ち続ける。その間は
  実際の接続数より最大でその台のぶんだけ多く数える。寿命を縮めると更新の往復が増える。
- 接続が開いている限りリースは更新され、寿命切れで落とされたあとでも更新で数え直される。
  Redis が一時的に落ちて復旧した直後は、生きている接続が上限を超えて数え直されうる。
  開いている接続を切るほうが損なので、この超過は許容する。
- 接続 1 本につき更新のゴルーチンが 1 本増える。1,000 接続で 1,000 本になるが、既存の
  読み取り・書き込み・ハートビートに 1 本足す形になる。
- Redis が応答しないとハンドシェイクは 500 で失敗する。接続数を数えられない状態で
  通すと上限が意味を失うため、通さない側に倒している。
- 上限に達したときのクライアント側の表示（「現在混み合っています」）は、チャット UI を
  作る段で 503 を受けて出す。ここで決めたのはステータスコードと `Retry-After` までとする。
- 見直す条件: 負荷試験で拒否が定常的に出る、または異常終了後にリースが切れるまでの 30 秒が
  運用上長すぎると分かったら、リースの寿命と上限値を見直す。
