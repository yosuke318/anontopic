# ADR-0005: 匿名セッションを Redis 上の不透明トークンと HttpOnly Cookie で持つ

- ステータス: Accepted
- 日付: 2026-08-21
- 関連 issue: YOSUKE-121, YOSUKE-124, YOSUKE-132

## 文脈

このサービスは会員登録を持たない。利用者を識別する手段はセッショントークンだけで、
`conversation_participants.session_token` や `messages.sender_token`（いずれも VARCHAR(64)）は
これを保存する前提でスキーマが決まっている。

判断に効く事実。

- **匿名性と BAN の実効性を両立させる必要がある。** 個人を永続的に特定しないまま、
  通報された利用者を締め出せなければならない。
- **BAN は即時に効く必要がある。** 迷惑行為の最中に BAN するため、接続済みの相手を
  その場で切れないと意味がない。
- クライアントはブラウザ。**ブラウザの WebSocket API はカスタムヘッダを付けられない**ため、
  ハンドシェイクに認証情報を載せる手段は Cookie かサブプロトコルに限られる。
- Redis は既にマッチングキューと presence 用に立っており、2 台のサーバーが同じものを見る。
- 保持ポリシーは会話とメッセージを 90 日で消す。セッションはそれより遥かに短命で、
  監査対象でもない。

## 決定

セッションを次の形で持つ。

- トークンは 32 バイトの暗号論的乱数を base64url にした 43 文字の**不透明な文字列**。
  中身に意味を持たせない。
- 実体は Redis の `session:{token}`（`ip_hash` と `issued_at`）に置き、**TTL が無操作失効を表す**。
  アクセスのたびに TTL を延長し、**無操作 24 時間 / 発行から絶対 7 日**で失効する。
- クライアントへは **HttpOnly Cookie**（`anontopic_session`、`Secure`、`SameSite` は設定可能）で渡す。
- 接続元 IP は鍵付きハッシュ（HMAC-SHA256）にして `ip_hash` として持ち、生の IP は保存しない。
  鍵は `SESSION_IP_HASH_SECRET` で環境ごとに固定する。
- `session_ip:{ip_hash}` にトークンを索引し、BAN が 1 回の呼び出しで同一ハッシュの
  セッションをすべて失効させられるようにする。

## 検討した代替案

### 案A: JWT を発行してサーバー側に状態を持たない

検証が速くストアが要らないが、**BAN の即時失効に失効リストが必要**になり、結局ストアを持つ。
状態を持たない利点が消え、失効リストと有効期限の二重管理だけが残る。

### 案B: PostgreSQL に `sessions` テーブルを作る

調査はしやすいが、接続のたびに UPDATE が走り、期限切れ行の掃除バッチも要る。
セッションは 90 日保持ポリシーの対象外の短命データで、**永続化する理由がない**。

### 案C: localStorage に置き、Authorization ヘッダで送る

オリジンをまたぐ構成に強い一方、**XSS でトークンをそのまま持ち出せる**。
WebSocket ではヘッダを付けられないため、URL かサブプロトコルに載せることになり、
URL に載せるとアクセスログやリファラに漏れる。

### 案D: 生の IP を保存する

BAN と発信者情報開示には十分だが、**匿名サービスが生 IP を保持する**ことになる。
ハッシュでも同一性の判定はできるため、保持する必要がない。

## 影響

- **`SESSION_IP_HASH_SECRET` を失うと、それ以前のハッシュに紐づく BAN が効かなくなる。**
  環境変数として管理し、無設定の場合はプロセス起動ごとの乱数になる（ローカル開発向け）。
- Redis が飛ぶと全利用者のセッションが切れる。会話中でも再入室が必要になるが、
  匿名の一時セッションなので復旧手段は用意しない。
- **Cookie 方式は CSRF を自分で塞ぐ必要がある。** WebSocket のハンドシェイクは Origin を
  検証し、許可オリジンは `APP_ALLOWED_ORIGINS` で与える。
- フロントエンドを API と別サイトに置く場合、Cookie は `SameSite=None; Secure` が必要になる。
  ホスティング方針（YOSUKE-140）が決まった時点で設定値を確定させる。
- トークンのローテーションは行わない。絶対有効期限で切れた後に新しいトークンを発行する。
  BAN 回避が実測で問題になったら、`ip_hash` 以外の識別子（YOSUKE-132）と合わせて再検討する。
