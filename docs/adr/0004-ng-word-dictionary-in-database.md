# ADR-0004: NG ワード辞書を DB のテーブルで持つ

- ステータス: Accepted
- 日付: 2026-08-21
- 関連 issue: YOSUKE-119, YOSUKE-129

## 文脈

NG ワード辞書は一次フィルタの実体だが、設計書 4.1 のテーブル一覧に格納先が無く、
DB とリポジトリ内のファイルのどちらで持つかが決まっていなかった。

判断に効く事実。

- 辞書は**運用しながら継続的に直す**もの。誤検知の報告や新しい隠語が出るたびに触る。
  初期リリース直後がもっとも変更頻度が高い。
- 判定はメッセージ送信のたびに走るため、辞書を都度読みに行くことはしない。
  起動時にメモリへ載せ、定期的に読み直す前提。
- サーバーは 2 台構成。両方が同じ辞書を見る必要がある。
- 運営用の管理画面は通報対応のために作る（YOSUKE-131）。

## 決定

`ng_words` テーブルで持つ。`word` に一意制約を置き、`category` で分類、
`is_active` で個別に無効化できるようにする。

`category` は次の 5 つとする。まとめて有効・無効を切り替えられるようにするための分類で、
判定の強さを変えるものではない。

| category | 対象 |
| --- | --- |
| `meetup` | 待ち合わせ・対面を促す語 |
| `dating` | 交際・出会いを目的とする語 |
| `sexual` | 性的な語 |
| `contact` | 外部連絡先の交換を促す語 |
| `solicitation` | 勧誘・スパム |

## 検討した代替案

### 案A: リポジトリ内のファイル（YAML / テキスト）で持つ

スキーマを増やさずに済み、変更が git の履歴とレビューに残る。
ただし**辞書を 1 語直すたびにデプロイが必要**になる。誤検知は利用者が困っている状態なので、
その場で消せないのは運用として弱い。変更頻度が高い初期ほど不利になる。

### 案B: Redis に持つ

読み込みは速いが、辞書は永続データであってキャッシュではない。
Redis が飛んだときに辞書が消えるのは事故になる。

### 案C: ファイルを基本とし、緊急時のみ DB で上書きする

両方の利点を取れるが、有効な辞書がどちらなのかを常に 2 か所見る必要がある。
1 名運用で持つ複雑さではない。

## 影響

- 設計書 4.1 のスキーマからの逸脱にあたる。設計書を更新する場合はこの ADR を根拠にする。
- 判定のたびに DB を引かないため、**辞書の変更が反映されるまでに定期リロードの間隔ぶん遅れる**。
  即時反映が必要になった場合はリロードの契機を足す（YOSUKE-129 の範囲）。
- 辞書の初期セットは誤検知を含む。表記揺れの正規化と語の調整は YOSUKE-129 で扱う。
  `is_active = false` にすれば語を消さずに止められる。
- 辞書の編集 UI は作っていない。当面は SQL で直す。管理画面に載せるかは YOSUKE-131 で判断する。
