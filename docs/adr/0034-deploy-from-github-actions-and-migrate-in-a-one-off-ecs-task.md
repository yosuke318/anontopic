# ADR-0034: GitHub Actions からデプロイし、マイグレーションは使い捨ての ECS タスクで流す

- ステータス: Accepted
- 日付: 2026-10-03
- 関連 issue: YOSUKE-139

## 文脈

- API は ECS Fargate で動き、Terraform はサービスが使うタスク定義のリビジョンを追わない
  （ADR-0029）。イメージの差し替えはデプロイ側で新しいリビジョンを登録して行う。
- RDS はプライベートサブネットにあり、GitHub Actions のランナーからは届かない。
  運用者は NAT インスタンス経由のポートフォワードで入っている（ADR-0032）。
- リポジトリは公開していて、Actions のログは誰でも読める。
- dev は追加開発のときだけ作り、普段は destroy している。開発体制は 1 名。
- 本番の ECS サービスはデプロイ中に新旧のタスクを並べる（最小 100% / 最大 200%）。
  ロールバックの間も、古いイメージと新しいスキーマが同時に動く。

## 決定

- main の CI が通ったら、GitHub Actions でイメージを 1 回だけビルドし、dev と prod の ECR に
  同じものを入れる。タグはコミットの SHA にする。
- dev は作られていれば承認なしで、prod は GitHub の Environment の承認を待ってからデプロイする。
- デプロイはファミリーの最新のタスク定義のイメージだけを差し替えて登録し、そのリビジョンで
  コマンドを `/migrate up` に替えた ECS タスクを 1 回動かしてから、サービスを切り替える。
- マイグレーションは後方互換のある変更に限る。列やテーブルの削除・改名は、それを使わない
  コードを先にデプロイしてから、別のマイグレーションで行う。
- ロールバックは、ECR にある過去のイメージで同じ手順を流す。マイグレーションは戻さない。
- デプロイ用の IAM ロール（`anontopic-deploy`）を Terraform の apply 用とは別に作り、ECR への
  push と ECS の操作に権限を絞る。

## 検討した代替案

### 案A: ランナーから直接マイグレーションを流す

RDS をランナーに開くか、ランナーを VPC に置く（セルフホスト）必要がある。前者は DB を
インターネットにさらし、後者は 1 名運用で面倒を見るものが増える。

### 案B: サーバーの起動時にマイグレーションを流す

2 タスクが同時に起動して競合し、失敗するとサービスごと起動しなくなる。golang-migrate の
ロックで競合は防げるが、失敗したときに切り戻す境目が無い。

### 案C: ロールバックでマイグレーションも戻す（`migrate down`）

down で消える列やテーブルのデータは戻らない。後方互換のある変更に限っていれば、古い
イメージは新しいスキーマでも動くため、戻す必要が無い。

### 案D: dev と prod で別々にビルドする

同じコミットからでも、ベースイメージの更新などで中身が変わりうる。dev で確かめたものと
違うイメージが prod に入る。

### 案E: Terraform の apply 用のロール（AdministratorAccess）でデプロイする

ロールを分ける手間は省けるが、毎回のデプロイで管理者権限を引き受けることになる。

## 影響

- 列の削除や改名は 2 回のデプロイに分ける必要がある。
- イメージにマイグレーションのバイナリも入る。ECS の RunTask は ENTRYPOINT を上書きできない
  ため、イメージは ENTRYPOINT を使わず CMD でサーバーを起動する。
- prod の承認を待つデプロイは、main に新しいコミットが入ると新しいものに置き換わる。
- マイグレーションが失敗するとサービスは切り替えず、ログは CloudWatch Logs で見る。
  Actions のログにはタスクの ID と終了コードだけを出す。
- 見直す条件: 後方互換を保てないスキーマ変更がどうしても要るとき、または運用者が増えて
  承認の流れを変えるとき。
