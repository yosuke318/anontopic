# ADR-0046: 人数の節目の通知は、ログに書いた最大人数から CloudWatch のアラームで送る

- ステータス: Accepted
- 日付: 2026-11-05
- 関連 issue: YOSUKE-233

## 文脈

- 公開したばかりで利用者が少ない。誰かが来たらすぐ知りたい。待機中と会話中の人数の合計が
  1 人、10 人、100 人に届いたときに、運用者にメールで知らせたい。
- 同じ節目で何度も知らせない。人数が 0 に戻ったら、次に来た人からまた知らせる。10 人の前後で
  人数が増減しても、0 に戻るまでは 10 人の通知は 1 回だけにする。
- 待機中は `matching:queue:*`、会話中は `chat:topic-presence:*` にあり（ADR-0042）、
  `topicPresence`（`cmd/server/main.go`）がトピックごとに数えられる。
- API のサーバーは 2 タスクで動く（ADR-0029）。どちらのタスクも同じ Redis を読む（ADR-0031）。
- アラームと予算の通知は、SNS トピック 1 つから運用者のメールに届けている（ADR-0033）。
- アプリは AWS の API を呼ばない。タスクロールも付けていない。ログは CloudWatch Logs に出ている。

## 決定

- 新しいモジュール `internal/activity` が、10 秒ごと（`ACTIVITY_INTERVAL`）に人数の合計を数え、
  0 人に戻ってから届いた最大の人数を Redis（`activity:peak`）に記録して、
  `{"msg":"activity","users":<合計>,"peak":<最大>}` をログに書く。0 人のときに最大を 0 に戻す。
- Terraform で、このログから `peak` をメトリクスに拾うメトリクスフィルタと、`peak` の 1 分の最大が
  1・10・100 以上になったら既存の SNS トピックに送るアラームを作る（`infra/modules/monitoring/activity.tf`）。
  状態が戻ったときの通知は付けない。
- 人数を数えられなかったとき（Redis や PostgreSQL が答えない）はログを書かない。0 人と読まれて
  最大が 0 に戻り、同じ節目が鳴り直すのを防ぐ。

## 検討した代替案

### 案A: アプリから SNS に直接 Publish する

通知の文面を自由に書け、トピックごとの内訳も載せられる。ただ、AWS SDK とタスクロールを足して、
アプリが AWS の API を呼ぶ作りに変わる。権限の管理と、2 タスクのどちらが送るかの取り決めも要る。
今回の要件は「届いた」と分かれば足りる。

### 案B: 人数の合計そのものにアラームを張る

アプリに最大人数を持たなくて済む。ただ、10 人のアラームは 9 人に下がった時点で戻り、また 10 人に
なると鳴り直す。節目の前後で人数が揺れると何度もメールが来て、0 人に戻るまで 1 回という要件を満たせない。

### 案C: Slack や Discord の Webhook に送る

スマホに即座に届く。ただ、Webhook の URL を秘密として置く必要があり、送るのは案A と同じくアプリになる。
メールはすでに予算とアラームで使っている。

## 影響

- 1 タスクあたり 10 秒に 1 行のログが増える（2 タスクで 1 日約 1.7 万行、数 MB）。カスタムメトリクス 1 つと
  アラーム 3 つの料金がかかる（どちらも月に数十円）。
- 通知が届くのは、人数が節目に届いてから 1〜2 分後になる。1 分の最大を見るので、10 秒以上いた人は数に入る。
- メールの文面は CloudWatch のアラームの書式になる（アラームの説明に日本語で何が起きたかを書いた）。
- `activity:peak` が消えた場合は、その時点の人数から数え直す。同じ節目がもう一度鳴ることがある。
- 利用者が増えて節目の通知が多すぎると感じたら、`activity_thresholds` を変えるか、アラームを外す。
