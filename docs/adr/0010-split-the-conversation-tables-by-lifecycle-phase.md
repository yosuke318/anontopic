# ADR-0010: 会話テーブルへの書き込みを matching と chat で分担する

- ステータス: Accepted
- 日付: 2026-08-28
- 関連 issue: YOSUKE-123, YOSUKE-124

## 文脈

CONTRIBUTING.md の「モジュール間の依存ルール」は、各モジュールが自分の所有するテーブルにのみ
アクセスすることを求めている。`conversations` と `conversation_participants` は、この規則に
そのまま当てはまらない。

- ルームの成立時に両方のテーブルへ行を書くのは `matching` である。
- 切断時に `conversations.ended_at` / `end_reason` を記録するのは `chat` である。切断を
  観測できるのは WebSocket 接続を持っているモジュールだけで、`matching` からは見えない。
- `chat` は接続してきたセッショントークンがその会話の参加者かどうかを `conversation_participants`
  で確かめる必要がある。確かめないと、会話 ID を知っているだけの第三者がルームに入れる。
- 3 人ルームの表示に使う参加者の並び（1 人目 / 2 人目 / 3 人目）も同じ表から読む。
  サーバーが複数台あるため、全サーバーで同じ並びになる必要がある。

所有者を決めないまま実装すると、どちらのモジュールも同じテーブルに好きな操作を足していく
ことになる。

## 決定

テーブル単位ではなく、会話のライフサイクルの局面で書き込みを分ける。

| テーブル | matching | chat |
| --- | --- | --- |
| `conversations` | ルーム成立時の INSERT | `ended_at` / `end_reason` の UPDATE |
| `conversation_participants` | ルーム成立時の INSERT | SELECT のみ（参加者の照合と並びの取得） |
| `messages` | 触れない | INSERT |

`chat` は `conversation_participants` に書き込まない。参加者の集合はルームが成立した時点で
確定し、以降は変わらない。

## 検討した代替案

### 案A: chat が matching のインターフェース経由で会話の終了を記録する

依存ルールの文面には最も素直に従う。ただし `matching` は待機キューとルーム割当だけを持つ
モジュールで、会話の終了は関心の外にある。終了を記録するためだけに API を持たせると、
`chat` → `matching` の依存が増え、将来どちらかを切り出したときにサービス間呼び出しが
切断のたびに発生する。

### 案B: conversation モジュールを新設し、matching と chat の両方から呼ぶ

テーブルの所有者が 1 つになり、規則の読み替えが要らなくなる。ただし基本設計書 1.2 の
モジュール構成に無いモジュールが増え、`matching` と `chat` の両方に薄い委譲層が挟まる。
テーブル 2 つ・操作 5 つの規模に対して間接層が見合わない。

### 案C: chat が入室時に conversation_participants へ INSERT ... ON CONFLICT DO NOTHING する

再接続で行が増えないことは ADR-0003 の一意制約が守るため、参加人数の判定は壊れない。
ただし会話 ID さえ知っていれば誰でも自分を参加者として書き込めてしまい、他人の会話に
入れる。照合だけにすれば、参加者になれるのはルーム成立時に選ばれた人だけになる。

## 影響

- `conversation_participants` の行を作るのは `matching` だけになる。`chat` の入室処理は
  照合なので、再接続しても行が増える余地が無い。
- CONTRIBUTING.md のルールをテーブル単位で読むと逸脱に見える。読み替えの根拠はこの ADR に置く。
- 会話の終了を書けるのは `chat` だけになる。参加者が接続していたサーバーが全て落ちると、
  `ended_at` が NULL のまま残る会話が生まれる。掃除は `retention` の担当として別に決める。
- 見直す条件: `chat` か `matching` を独立したサービスとして切り出すとき、案B の会話モジュールを
  再検討する。
