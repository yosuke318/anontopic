# ADR-0025: 自動の段階的制裁は端末 ID にかけ、IP ハッシュへの BAN は運営に任せる

- ステータス: Accepted
- 日付: 2026-09-24
- 関連 issue: YOSUKE-132

## 文脈

要件定義書 第4章は、通報頻度によるアカウント制限と、警告 → 一時停止 → 恒久停止の段階的制裁を
求めている。YOSUKE-132 は `banned_identifiers` への `ip_hash` / `device_fingerprint` の登録、
NG ワード検知回数と通報件数による自動制裁、手動の BAN と解除、共有 IP による巻き込みへの配慮を
求めている。

- 利用者は会員登録をせず、匿名のセッショントークン（最長 7 日、[ADR-0005](0005-anonymous-session-tokens-in-redis.md)）
  でしか区別できない。トークンは誰でも即座に取り直せるため、制裁の単位にならない。
- IP ハッシュはモバイル回線のゲートウェイ（キャリアグレード NAT）や学校・職場の回線では
  多数の利用者で同じ値になる。全年齢対象（要件定義書 3.3）のため、学校の回線は現実に起きる。
- `banned_identifiers.identifier_type` は設計書の時点で `device_fingerprint` を想定しているが、
  値をどう作るかは決まっていなかった。
- 通報は会話を指し、参加者を指さない（[ADR-0015](0015-report-a-conversation-rather-than-a-participant.md)）。
  3 人ルームでは通報者以外の 2 人のどちらが問題だったかを通報からは決められない。
- `conversation_participants` には、制裁の対象を後から引ける識別子が記録されていなかった。
- 運営は 1 名で、すべての制裁を人手で判断する時間はない。

## 決定

**端末 ID** を `device_fingerprint` として使い、自動の制裁はこれにだけかける。IP ハッシュへの
BAN は、会話を読んだ運営が管理 API（`POST /api/admin/bans`）からかける。

- 端末 ID は `POST /api/session` が発行する乱数で、HttpOnly Cookie（`anontopic_device`、1 年）に置く。
  セッションが切れても残り、次のセッションにも引き継ぐ。ブラウザの特徴から計算する
  フィンガープリントは使わない。
- ルームが成立したとき、matching が session から各参加者の IP ハッシュと端末 ID を読み、
  `conversation_participants.ip_hash` / `device_fingerprint` に記録する。
- 制裁の段階は `banned_identifiers.sanction`（`warning` / `suspension` / `permanent`）に持ち、
  警告も 1 行として残す。次の段階は、その識別子の解除されていない行の数で決める
  （0 件 → 警告、1 件 → 一時停止、2 件以上 → 恒久停止）。
- 自動の制裁のきっかけは 2 つ。NG ワードでブロックされた送信（既定: 最初の 1 通から 1 時間の
  うちに 5 通）と、通報者以外の参加者として通報された会話（既定: 最初の 1 件から 7 日のうちに
  3 会話）。どちらも Redis で端末 ID ごとに数え、段階を進めたら数え直す。
- 解除は行を消さず `lifted_at` を記録する。解除した行は効かず、段階の数にも入らない。
- BAN の判定は接続とマッチングのたびに行う。結果は Redis に最長 1 分置き、BAN と解除のたびに
  消す。一時停止はその残り時間より長く置かないため、期限が来れば何もしなくても解ける。

## 検討した代替案

### 案A: 自動の制裁も IP ハッシュにかける

回避されにくい。ただし共有 IP の利用者全員が、会ったこともない誰かの NG ワードで止まる。
通報による自動制裁は、通報を悪用して回線ごと止める手段にもなる。issue が求める巻き込みへの
配慮と正面から反する。

### 案B: ブラウザフィンガープリント（Canvas・フォント・画面サイズなどの組み合わせ）

Cookie を消しても同じ値になりやすく、回避に強い。ただし匿名性を原則とするサービスが利用者の
環境を収集することになり（要件定義書 第2部 9.4 のプライバシー配慮と合わない）、同じ機種・
同じブラウザの利用者どうしで値が衝突しやすい。学校で配られた同じ端末はまさに衝突する。
実装にも外部ライブラリか相応の実装量が要る。

### 案C: 共有 IP を検出して、共有 IP でないときだけ IP ハッシュにかける

回避に強く巻き込みも減らせる。ただし共有かどうかの判定には、同じ IP ハッシュから同時に来る
端末 ID の数などを実測してしきい値を決める必要があり、今はその測定がない。ASN による判定は
GeoIP の導入（設計書 第9章）が前提になる。

### 案D: 警告を banned_identifiers とは別の表に置く

`banned_identifiers` を「効いている BAN の一覧」として素直に読める。ただし段階を決めるために
2 つの表を数えることになり、監査の記録も 2 か所に分かれる。制裁の履歴は 1 か所で読めるほうが
運営 1 名の体制に合う。

## 影響

- **Cookie を消す、別のブラウザを使う、シークレットウィンドウを開くと、自動の制裁は回避できる。**
  回避された制裁は、運営が IP ハッシュへの BAN で止める。自動の制裁は「悪意の薄い利用者に
  段階を踏んで気づかせる」ためのもので、強い回避への対策ではない。
- 端末 ID を持たない利用者（この仕組みより前に発行されたセッションで入室した参加者）には、
  自動の制裁がかからない。セッションの絶対有効期限（7 日）で入れ替わる。
- 3 人ルームの通報は、通報者以外の 2 人の両方に数える。1 回の通報では制裁に至らず、
  3 つの別の会話で通報されて初めて警告になるため、巻き込まれた側が一度で止まることはない。
- 警告は取り消されるまで段階の数に残り、時間では消えない。1 年前の警告でも次は一時停止になる。
- `conversation_participants.ip_hash` / `device_fingerprint` は保持期間の管理対象になる。
  設計書 4.2 の IP 関連項目と同じく、retention の設計時に削除期間を決める。
- 見直す条件: 制裁の回避が運営の負担になるほど実測で増えたら、案C（共有 IP の判定）を検討する。
  誤って制裁された端末の解除依頼が目立つようになったら、しきい値か警告の失効を見直す。
