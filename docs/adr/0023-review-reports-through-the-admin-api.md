# ADR-0023: 通報の確認と対応は管理 API で提供し、画面は別リポジトリに置く

- ステータス: Accepted
- 日付: 2026-09-21
- 関連 issue: YOSUKE-131

## 文脈

YOSUKE-131 は、運営が通報一覧・会話ログを見て、対応ステータス（open / reviewing / actioned /
rejected）を更新できる最小限の管理画面と、そのアクセス制御を求めている。

- 管理画面は本体とは別リポジトリのアプリとして作り、当面デプロイせずローカルからのみ使う
  方針になっている。管理画面から PostgreSQL は直接触らず、Go の管理 API を経由する。
- 管理 API は `ADMIN_API_TOKEN` の Bearer トークンで守っている
  （[ADR-0007](0007-guard-the-admin-api-with-a-static-bearer-token.md)）。ADR-0007 は
  「管理画面を作る時点で書き直して supersede する」としている。
- 会話ログは `chat` が持つ `conversations` / `conversation_participants` / `messages` にある。
- 参加者のセッショントークンは、部屋の中でも他の参加者に渡さない値になっている。

## 決定

通報と申し立ての確認・更新は、`report` モジュールの管理 API（`/api/admin/reports`、
`/api/admin/claims`）として本体に置く。画面は別リポジトリの管理画面がサーバー側からこの API を
呼んで描く。

- 会話ログは `report` が `Conversations.Transcript` 経由で `chat` から受け取り、参加者を
  ルーム内の番号（1 起点）に置き換えて返す。セッショントークンは管理 API の応答に含めない。
- アクセス制御は ADR-0007 の方式をそのまま使う。トークンの検査は `internal/adminauth` に
  まとめ、`topic` と `report` の管理ハンドラが共有する。

ADR-0007 は supersede しない。管理画面はローカルからのみ使い、管理者も 1 名のままで、
ADR-0007 が方式を見直す条件（公開する管理画面・複数の管理者）にまだ当たらないため。

## 検討した代替案

### 案A: 管理画面を Next.js（`web/`）の中に作る

リポジトリが 1 つで済む。ただし利用者向けの公開サイトと同じ配信物に管理画面が載り、
トークンをブラウザに渡さない構成を別に組む必要がある。管理画面をローカル限定で動かす
方針とも合わない。

### 案B: 管理画面から PostgreSQL を直接読む

API を足さずに済む。ただし会話ログの読み方（参加者の並び、トークンの伏せ方）が Go の外に
複製され、テーブルの所有を決めた ADR-0010 の外から書き込みが入る余地もできる。

### 案C: 会話ログにセッショントークンをそのまま含める

BAN などの次の手当てに使える可能性はある。ただし BAN は IP ハッシュで行い
（`banned_identifiers`）、トークンは会話が終われば意味を持たない。運営の画面に出す必要のない
識別子を増やさない。

## 影響

- 誰が対応ステータスを変えたかは記録できない（共有トークンのため）。
- 管理 API の契約は docs/openapi.yaml が正で、管理画面のリポジトリはそれに合わせる。
- 見直す条件: 管理画面を公開環境にデプロイする、または管理者が 2 名以上になったら、
  ADR-0007 を supersede して操作者を識別できる認証に移す。
