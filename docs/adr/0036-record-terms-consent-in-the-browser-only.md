# ADR-0036: 利用規約への同意はブラウザにだけ記録し、会話を始める前に求める

- ステータス: Accepted
- 日付: 2026-10-06
- 関連 issue: YOSUKE-141

## 文脈

- 設計書 3 章は、出会い系サイト規制法に当たらないことを規約と導線の両面で示すことを求めている。
  サービスの目的（雑談・趣味・相談）と禁止行為を、利用者が会話を始める前に目にする必要がある。
- 会員登録は無く、利用者を識別するのは匿名のセッション（無操作 24 時間 / 発行から 7 日）と
  端末 ID の Cookie（1 年）だけ（ADR-0005、ADR-0025）。
- 会話に入る経路は `/topics` で待機を始めることだけで、`/waiting` と `/rooms/` はそこからしか
  たどれない。
- 規約の変更（定型約款の変更）は、変更後の内容と効力の発生日をサービス上に示せば足りる。
  変えるたびに全員から同意を取り直す仕組みまでは要らない。
- ブロックした参加者もブラウザの中だけで持っている（ADR-0016）。

## 決定

- `/topics` の「話しはじめる」の上に、目的の説明と、利用規約とプライバシーポリシーへの
  同意のチェックボックスを置く。チェックするまでボタンは押せない。
- 同意した規約の版（`termsVersion`）をブラウザの `localStorage` に記録し、同じ版に同意済みなら
  チェックボックスを出さない。版を上げると、次に会話を始めるときに同意を求め直す。
- 同意はサーバーに送らず、API も同意の有無を検査しない。
- 規約では「会話を始めた時点で同意したものとみなす」と定め、同意の記録が消えた場合も
  規約の適用の根拠を残す。

## 検討した代替案

### 案A: 同意をサーバーに記録する（`POST /api/session` で同意の版を受け取る）

API がセッションや端末 ID ごとに同意の版を持ち、無ければ待機を拒む。誰がいつ同意したかを
証明できるが、セッションも端末 ID も匿名で、その記録から本人にたどり着けない。
保存する情報が増える一方で、紛争のときに使える証拠にはならない。

### 案B: 初めて訪れたときにページ全体を覆うモーダルで同意を求める

LP と紹介ページは検索から入ってくるページで、本文を覆うと SEO と AdSense の審査に響く
（ADR-0014）。会話を始める操作の直前で求めれば足りる。

### 案C: 同意の記録を Cookie に置く

サーバーが読まないのに、すべての要求に付いて送られる。

## 影響

- ブラウザのストレージを消すか、別のブラウザを使うと、もう一度同意を求められる。
  ストレージを使えないブラウザでは毎回求められる。
- API を直接呼ぶクライアントは、同意の画面を通らずに会話できる。規約は会話を始めた時点で
  同意したものとみなす定めで、この場合にも適用する。
- 規約を変えて同意を取り直すときは、`web/lib/terms.ts` の `termsVersion` と制定日を上げる。
- 見直す条件: 同意の記録をサーバー側で証明する必要が出たとき（法令の改正、専門家のレビューでの指摘、
  会員登録の導入）。
