# ADR-0043: トピック別の需要を Redis で数え、日ごとの合計だけを残す

- ステータス: Accepted
- 日付: 2026-11-01
- 関連 issue: YOSUKE-148

## 文脈

- どのトピックが求められているかを知りたい。`conversations` は成立した会話しか持たないため、
  待ったが相手が見つからなかったトピックは現れない。3 人ルームはこの偏りが大きい。
- 待機列は Redis の sorted set（`matching:queue:{topicID}:{roomType}`、ADR-0008）にあり、
  入る・ルームが成立して出る・自分でやめる、はどれも Lua スクリプトで 1 回にまとめて動かしている。
- 同時接続の上限は 1,000。利用者は相手を探し直すたびに待機列に入り直す。
- 参加者は一時的なセッショントークンだけで表し、識別子は 180 日で消す（ADR-0037）。
- Redis は 1 ノード（ADR-0031）。日次のバッチは毎日 05:00（日本時間）に動く（ADR-0041）。

## 決定

- 待機列のスクリプトが、日（日本時間）ごとの hash（`matching:demand:{YYYY-MM-DD}`）に、
  キューごとの数を足す。数えるのは、入った人数・成立した人数・自分でやめた人数・成立した人の待ち時間の合計。
  hash は最後に書いてから 8 日で消える。
- retention バッチ（`cmd/retention`）が、過去 7 日分の hash を `topic_daily_stats` に書き写す。
  1 日分を丸ごと書き直すので、何度流しても同じ結果になる。Redis に残っていない日は書き換えない。
- 利用者ごとの明細は残さない。同じ人が入り直したら、その回数だけ数える。
- 2 人ルームと 3 人ルームは分けて数える。3 人ルームを選び 2 人で成立した人も、3 人ルームの側に数える。
- `conversations` のインデックスを `(topic_id)` から `(topic_id, started_at)` に替え、期間で絞った
  トピック別の集計に使えるようにする。

## 検討した代替案

### 案A: 入るたびに明細を PostgreSQL に書く

成立したか・なぜ出たかを 1 件ずつ追える。ただ、探し直しのたびに行が増え、マッチングの
経路に DB の書き込みが 1 回足される。明細を消す処理も retention に要る。欲しいのは日ごとの数だけだった。

### 案B: 入るたびに `topic_daily_stats` を直接 UPSERT する

明細は要らない。ただ、人気のあるトピックでは同じ行に書き込みが集まり、行ロックで待つ。
マッチングの経路に DB の書き込みが入る点も案A と同じ。

### 案C: 同じ人の入り直しを 1 件にまとめる

需要の人数に近い数になる。ただ、まとめるにはトークンかハッシュ化した IP を、少なくとも
その日のあいだ残すことになる。集計のために識別子を増やしたくない。

### 案D: 2 人ルームと 3 人ルームを分けない

行は半分になる。ただ、3 人ルームが成立しにくいことが合計に埋もれて見えなくなる。

## 影響

- 時間切れで出た人数は直接数えない。入った人数から、成立した人数と自分でやめた人数を引いて求める。
  入ったのと出たのが日をまたいだ人の分だけずれる。
- ルームが Redis で成立したあと、会話を DB に書くのに失敗すると、成立した人数に数えたまま
  参加者は待機列に戻る。戻った人は入り直すので、入った人数も 1 回多くなる。
- retention バッチが Redis にもつなぐ。需要の書き写しに失敗しても `retention failed` を出すので、
  既存のアラームで気づける。7 日続けて失敗すると、それより前の日の数は失われる。
- 見直す条件: 需要の人数を正確に知りたくなったら案C、成立しなかった理由を 1 件ずつ見たくなったら案A を検討する。
