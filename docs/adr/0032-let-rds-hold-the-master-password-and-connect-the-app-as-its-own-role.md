# ADR-0032: RDS のマスターパスワードは RDS に持たせ、アプリは専用のロールで接続する

- ステータス: Accepted
- 日付: 2026-10-03
- 関連 issue: YOSUKE-137

## 文脈

- RDS のインスタンスを作るには、マスターユーザーのパスワードを決める必要がある。
  YOSUKE-137 は、認証情報を tfstate に平文で残さないことを求めている。
- サーバーは `DATABASE_URL` を SSM パラメータストアから読み、値は運用者が Terraform の外で
  入れる（ADR-0030）。
- RDS に Secrets Manager のシークレットでマスターパスワードを持たせると、state に値は入らない。
  ただしそのシークレットは既定で 7 日ごとにローテーションされる。
- リリースイメージにはサーバーしか入っておらず、シェルも無い。マイグレーションは
  運用者の手元から流す必要がある。
- RDS はプライベートサブネットにあり、外から直接届かない。NAT インスタンスはパブリック
  サブネットにあり、Session Manager で入れる（ADR-0028）。

## 決定

- マスターパスワードは `manage_master_user_password` で RDS に作らせ、Secrets Manager に置く。
  マスターユーザーは運用者だけが使う。
- アプリは運用者が作るロール `anontopic_app` で接続する。このロールをデータベースの所有者にし、
  マイグレーションも同じロールで流す。パスワードは `DATABASE_URL` に含めて SSM に入れる。
- 運用者は、NAT インスタンスへの Session Manager のポートフォワードで RDS に入る。
  RDS のセキュリティグループは、アプリに加えて NAT インスタンスからの 5432 を受け付ける。

## 検討した代替案

### 案A: アプリもマスターユーザーで接続する

ロールが 1 つで済む。ただしローテーションのたびに SSM の `DATABASE_URL` が古くなり、
アプリが接続できなくなる。

### 案B: パスワードを Terraform の変数で渡す

`password` で渡すと値が state に入る。書き込み専用の `password_wo` なら state には入らない。
ただし、CI の plan も含めて実行のたびに値を渡す必要がある。

### 案C: 踏み台のインスタンスを別に立てる

NAT インスタンスとは役割が分かれる。ただし月数ドルとパッチ当ての手間が 1 台分増える。
NAT インスタンスには Session Manager の設定が既にある。

### 案D: マイグレーションを ECS の単発タスクで流す

運用者の手元から RDS に届く経路は要らなくなる。ただし migrate 用のイメージとタスク定義が増える。
ロールを作るときには、結局 psql で入る必要がある。

## 影響

- マスターのシークレットに月 $0.40 かかる（環境ごと）。
- 環境を作ったら、運用者が README の手順でロールを作り、マイグレーションを流し、
  `DATABASE_URL` を入れる。それまでアプリは DB に接続できない。
- NAT インスタンスから RDS に届くため、NAT インスタンスに入れる IAM 権限があれば
  DB に接続を試みられる。パスワードが無ければ入れない。
- 見直す条件: CI からマイグレーションを流すことにしたときは、案D の単発タスクに移し、
  NAT インスタンスからの通信を閉じる。
