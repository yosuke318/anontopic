# ADR-0047: 管理画面へのログインは Cloudflare Access に任せ、管理 API のトークンはそのまま使う

- ステータス: Accepted
- 日付: 2026-11-06
- 関連 issue: YOSUKE-231
- Supersedes: ADR-0007

## 文脈

ADR-0007 は、管理画面ができた時点で管理 API の守り方を見直すと決めていた。その管理画面ができた。

- 管理画面（`anontopic-admin`、Rails）はラズパイの Docker で動く。DB を持たず、本体の管理 API
  （`/api/admin/*`）を `ADMIN_API_TOKEN` で呼ぶ。トークンは Rails のサーバー側だけに置き、ブラウザには渡さない。
- 今は SSH のポート転送でしか開けない。外出先からも開けるようにしたい。家のルーターのポートは開けたくない。
- 管理者は開発者 1 名。管理操作は通報の対応、BAN、トピックの管理で、件数は少ない。
- `anonymtopic.com` のゾーンは Cloudflare にある（ADR-0040）。Cloudflare Zero Trust は 50 ユーザーまで無料で使える。
- 管理者は Google のアカウントを持っていて、2 段階認証とパスキーを Google 側で必須にできる。

## 決定

- **人のログインは Cloudflare Access に任せる。** ラズパイの `cloudflared` から Cloudflare Tunnel を張り、
  `admin.anonymtopic.com` を Access のアプリケーションの内側に置く。ログイン方法は Google（OIDC）だけにし、
  許可したメールアドレスだけを通す。OIDC の RP（クライアント）になるのは Access で、Rails ではない。
- **Rails は Access が署名した JWT（`Cf-Access-Jwt-Assertion`）を確かめる。** 発行元（チームのドメイン）と
  AUD タグを照合し、確かめられないリクエストは 403 で断る。Tunnel を通らずに届いたリクエストへの備えで、
  鍵は Access が公開するもの（`/cdn-cgi/access/certs`）を取りに行く。誰が開いたかは、トークンの
  メールアドレスを Rails のログに残す。
- **本体の管理 API は `ADMIN_API_TOKEN`（ADR-0007）のまま守る。** 管理画面のサーバーと本体のサーバーの間の
  信頼で、人のログインとは別に扱う。本体は Access も OIDC も知らない。

## 検討した代替案

### 案A: Rails にログイン機能を作り、それを唯一の守りにする

パスキーや TOTP の 2 段階認証を自分で実装し、ルーターのポートを開けて公開することになる。
認証の実装の誤りがそのまま管理画面の公開につながり、家のネットワークにも入口ができる。
Rails 側のログインは学習のために後から足すが、それを外への唯一の守りにはしない。

### 案B: 本体の管理 API を OAuth のリソースサーバーにする

管理画面が利用者のアクセストークンを持って API を呼び、本体が誰の操作かを知れる。ただ、本体に
トークンの検証と権限の管理を足すことになる。管理者 1 名に対して変更が大きく、ADR-0007 の
トークンで今は足りている。

### 案C: VPN（Tailscale など）で家のネットワークに入る

ポートを開けずに済む。ただ、管理画面を開く機器すべてにクライアントを入れる必要がある。
Access ならブラウザだけで開け、ログインの強さは Google 側の 2 段階認証で決まる。

## 影響

- Cloudflare に障害があると、外から管理画面を開けない。そのときは SSH のポート転送で開く
  （Access の確認を切る手順は `anontopic-admin` の README にある）。
- 管理 API のトークンは 1 個の共有の値のままで、本体のログには誰の操作かが残らない。誰が開いたかは
  管理画面のログ（Access のメールアドレス）でしか追えない。
- 管理者が 2 名以上になる、または本体の側で操作者を記録する必要が出たら、操作者を本体に渡す方法
  （案B を含む）を検討し、この ADR を supersede する。
