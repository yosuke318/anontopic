# ADR-0015: 通報は相手ではなく会話を対象にする

- ステータス: Accepted
- 日付: 2026-09-06
- 関連 issue: YOSUKE-128

## 文脈

チャットルーム画面に通報ボタンを常設する（設計書 第7章）にあたり、何を通報の対象に
するかを決める必要がある。

- 参加者は会員登録を持たず、部屋の中では会話ごとの参加者番号（1 起点）でしか区別
  できない。番号は会話ごとに振り直されるため、部屋の外では誰も指さない。
- セッショントークンは他の参加者に渡らない。ブラウザには通報相手を名指しできる識別子が
  そもそも無い。
- `reports` テーブルは会話 ID と通報者のトークンを持ち、対象の参加者を持たない
  （マイグレーション 000001）。
- 通報の受付と管理画面は M2 の別 issue が持つ。この issue で用意するのは受け口だけで、
  レビューの導線はまだ無い。

## 決定

`POST /api/reports` は会話 ID と分類（`reason`）だけを受け取り、通報の対象は会話とする。
通報できるのはその会話の参加者に限り、参加していない会話と存在しない会話は区別せず
403 を返す。同じ会話を同じ通報者が繰り返し通報しても記録は増やさない
（`reports` に会話 ID と通報者の一意制約を置く）。

分類は `sexual` / `contact` / `harassment` / `spam` / `other` の 5 つに固定する。
要件定義書 3.2 の禁止行為に対応させ、同じ種類の通報を数えられるようにするため。

## 検討した代替案

### 案A: 通報時に参加者番号を送り、相手を特定する

サーバー側では番号から会話参加者の行を引けるため、技術的には可能。ただし部屋の中の
番号を部屋の外に出すことになり、番号と個人を結びつける情報がクライアントに増える。
2 人ルームでは会話を通報することと相手を通報することが実質同じで、3 人ルームでも
運営は会話ログ全体を読んで判断する。番号を受け取っても判断材料は増えない。

### 案B: 分類を自由入力にする

利用者が状況を説明できる一方、集計ができない。段階的制裁（要件定義書 第4章）は
通報の傾向を数えて判断するため、自由文だけでは運用に乗らない。将来、分類に加えて
補足の自由入力を足すことはできる。

### 案C: 押されたぶんだけ記録する

会話に付く通報の数が、通報した人数ではなくボタンを押した回数になる。制裁の判断に
使う数として意味を持たなくなるため採らない。

## 影響

- 運営は「この会話に通報が何件付いたか」までしか分からない。3 人ルームで特定の 1 人が
  問題だった場合、会話ログを読んで判断することになる。
- 分類を増やすときは Go 側の定数・openapi・フロントの選択肢を揃えて足す。
  古い分類の行は残るため、削除ではなく追加で運用する。
- 会話が終わった後も通報できる。退出してから通報する導線を残すため、
  参加者かどうかの判定は会話の終了を見ない。
