# ADR-0012: メッセージの書き込みをバッファして一括 INSERT する

- ステータス: Accepted
- 日付: 2026-08-29
- 関連 issue: YOSUKE-125

## 文脈

チャットの送信経路は、モデレーション → `messages` への INSERT → Redis への publish の順に進む。
INSERT を 1 件ずつ発行すると、DB との往復がそのまま参加者の体感するレイテンシに乗る。

- 同時接続の上限は 1,000（設計書 2）。全員が会話していれば毎秒数百件の INSERT になる。
- 予算上限は月額 4 万円（設計書 6）で、RDS は Multi-AZ の小さいインスタンスを 1 台だけ置く。
  書き込みの往復回数が増えるほど、接続数と CPU の余裕が削られる。
- メッセージを保存する目的は、通報の突き合わせと発信者情報の保存（設計書 3.4 / 4.2）である。
  参加者に履歴を見せる API は無く、保存した行を読むのは管理側とバッチだけ。
- 配信イベントの `id` は INSERT の `RETURNING id` から取っている。非同期にすると、
  配信の時点で DB の採番を持てない。
- `messages` は `created_at` のレンジパーティション。行がどのパーティションに入るかは
  `created_at` だけで決まる。

## 決定

`messages` への書き込みを送信経路から外す。chat はメッセージをプロセス内のバッファに積み、
100 件たまるか 200 ミリ秒経つかのどちらか早い方で、1 回の往復にまとめて INSERT する。

- `created_at` はサーバーが送信を受け付けた時刻を明示的に入れる。参加者に返した `sent_at` と
  保存される時刻が一致し、行の入るパーティションも受け付けた時点で決まる。
- 配信イベントから DB の `id` を落とす。メッセージは `participant` と `sent_at` で表す。
- バッファが埋まっている間、送信した接続はバッファに空きが出るまで待つ。メッセージは捨てない。
- 終了時はバッファに残っているぶんを書いてから止まる。

## 検討した代替案

### 案A: 1 件ずつ同期で INSERT する

実装が最も単純で、書き込みに失敗したメッセージを配信せずに済む。ただし DB の往復がレイテンシに
そのまま乗り、同時接続 1,000 で毎秒数百回の往復を小さな RDS 1 台に当てることになる。

### 案B: 非同期にしつつ、シーケンスをブロックで先取りして `id` を配信に残す

protocol を変えずに済む。ただし採番の仕組みを別に持つことになり、プロセスが落ちるたびに
先取りした番号が飛ぶ。クライアントは `id` を使っておらず、保つために増える実装量に見合わない。

### 案C: バッファが埋まったらメッセージを捨てる

書き込みが詰まってもチャットのレイテンシは落ちない。ただし通報を受けたときに、その会話の
メッセージが揃っている保証が無くなる。保存の目的が法令対応である以上、欠落は許容できない。

### 案D: Redis のリストに積み、別プロセスが読んで書く

プロセスが落ちてもメッセージが残り、書き込みの詰まりがアプリケーションから切り離される。
ただし常駐プロセスが 1 つ増え、EC2 2 台（設計書 5）の構成に別役割のプロセスを足すことになる。
失われる窓が数百ミリ秒である今の規模には見合わない。

## 影響

- プロセスが落ちると、バッファに残っていたメッセージが失われる。バッファはバッチ 4 本ぶん
  （既定 400 件）まで積むため、書き込みが詰まっているときほど失う量が増える。停止シグナルを
  受けた場合は書いてから止まるので、失われるのは異常終了のときだけになる。
- 書き込みの失敗は配信の後に起きるため、送信者にはエラーが返らない。ログにだけ残る。
- クライアントはメッセージに DB の `id` を持たない。`participant` と `sent_at` で表示する。
- `created_at` がサーバーの時計になる。サーバー 2 台の時計がずれているぶん、保存された順序が
  参加者の見た順序と入れ替わりうる（ミリ秒の単位）。
- 見直す条件: 負荷試験（YOSUKE-144）で書き込みが詰まる、または異常終了時の欠落が運用上
  問題になると分かったら、案D を再検討する。
