# ADR-0006: トピック一覧をプロセス内メモリにキャッシュする

- ステータス: Accepted
- 日付: 2026-08-26
- 関連 issue: YOSUKE-122

## 文脈

`GET /api/topics` はトピック選択画面が必ず呼ぶため、サービスへの入り口で最も
リクエスト数が多いエンドポイントになる。

判断に効く事実。

- `topics` は 8 行程度で、増えるとしても数十行。1 行は ID・名前・有効フラグだけで、
  一覧全体でも数 KB に収まる。
- 内容が変わるのは管理操作をしたときだけで、通常運用では月に数回あるかどうか。
- API サーバーは 2 台構成で、どちらも同じ PostgreSQL と Redis を見る。
- 開発・運用体制は 1 名。キャッシュの不整合を追いかける余力がない。
- Redis は既にセッションとマッチングキューで使っており、こちらは即時性が要る用途。

## 決定

有効なトピック一覧を **API サーバーのプロセス内メモリに TTL 付き（既定 5 分、
`TOPIC_CACHE_TTL` で変更可能）でキャッシュする**。管理 API の作成・更新・削除は、
書き込んだサーバーのキャッシュを即座に捨てる。

TTL が切れたときに PostgreSQL を読むのは 1 リクエストだけで、同時に来た他の
リクエストはその結果を待つ。

## 検討した代替案

### 案A: Redis にキャッシュする

トピック一覧の読み出しがネットワーク往復のままになり、PostgreSQL を Redis に
置き換えただけになる。無効化を全台に効かせられる利点はあるが、そのために
Pub/Sub と失敗時の扱いを持ち込むほど更新頻度が高くない。

### 案B: キャッシュせず毎回 PostgreSQL を読む

数 KB の固定的なデータに対して、入り口で最も多いリクエストがそのまま DB 接続を
消費する。2 台構成のコネクション数に対して割に合わない。

### 案C: 起動時に読み切って以後更新しない

管理 API でトピックを足しても、再起動するまで選択画面に出ない。管理画面を
後から作る前提と噛み合わない。

## 影響

- 管理操作の結果が全台に反映されるまで最大で TTL 分（既定 5 分）遅れる。
  トピックを非公開にしても、その間は片方のサーバーがまだ返す。
- 各サーバーが自分のコピーを持つため、台数を増やしてもキャッシュのための
  ミドルウェアは増えない。
- 選択画面以外からもトピック一覧を高頻度で引くようになったら、あるいは管理操作の
  即時反映が要件になったら、Redis と Pub/Sub による無効化を再検討する。
