# ADR-0009: 3人ルームは待機上限に達したら2人ルームへ切り替える

- ステータス: Accepted
- 日付: 2026-08-27
- 関連 issue: YOSUKE-123

## 文脈

3 人ルームのマッチング待機時間の許容上限は、設計書 第10章で未確定として残っていた。
決めなければ、3 人目が来ない待機列の扱いが実装できない。

- 3 人ルームは 3 人揃うまで成立しない。深夜やサービス初期のように同時に待つ人が少ない
  時間帯では、3 人目が来る保証がない。
- 会員登録が無いサービスのため、待たされた利用者はそのまま離脱する。戻ってくる導線が無い。
- `conversations.room_type` は参加人数そのもの（2 または 3）を持つ。2 人で成立させた会話は
  `room_type = 2` としてそのまま表せる。

## 決定

3 人ルームの待機列の先頭が `MATCHING_FALLBACK_AFTER`（既定 60 秒）を超えて待っていて、
2 人以上が並んでいるなら、先頭の 2 人で `room_type = 2` の会話を成立させる。

## 検討した代替案

### 案A: 上限を設けず、3 人揃うまで待たせる

実装は最も単純になる。ただし人が少ない時間帯は永久に成立せず、
利用者は待機画面のまま離脱する。「相手がいる時間帯にしか使えない」体験になる。

### 案B: 上限で待機を打ち切り、成立しなかったことを返す

挙動は明快だが、利用者に 2 人ルームを選び直させる操作が増える。
その操作をせずに離れる利用者のぶん、成立率は 3 案の中で最も低くなる。

## 影響

- 3 人を選んだ利用者が 2 人ルームに入ることがある。API は成立した `room_type` を返すので、
  クライアントはその値で画面を描く。
- 60 秒という値は実測なしで決めている。離脱率と、2 人で成立した会話の割合を見て見直す。
- フォールバックは、待っている利用者自身の `GET /api/matching` が引き金になる。
  誰も状態を問い合わせない待機列では成立しない。
