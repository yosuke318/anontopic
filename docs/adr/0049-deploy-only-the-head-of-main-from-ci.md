# ADR-0049: CI からのデプロイは main の先頭のコミットだけを入れる

- ステータス: Accepted
- 日付: 2026-11-09
- 関連 issue: なし

## 文脈

- prod へのデプロイは、GitHub の Environment の承認を待ってから動く（ADR-0034）。
- 同じ環境へのデプロイは `concurrency` で 1 つずつ流している。ただ、承認を待っている間の実行は
  この順番待ちに入っていない。承認待ちのデプロイが複数あると、どれも承認待ちのまま並び、
  承認した順に動く。
- Actions の "Re-run all jobs" は、元の実行と同じコミットでビルドとデプロイをやり直す。
- 2026-11-09 に、11/4 のコミット `9363ce2` の実行を再実行して承認したところ、先に入っていた
  `2836732`（PR #45）を上書きし、prod の API とフロントエンドが古い版に戻った。
- 開発・運用は 1 名で、承認する人がどの実行が新しいかを毎回見比べるのは当てにできない。

## 決定

CI から動いたデプロイ（dev と prod）は、承認されて動き出した時点で、入れるコミットが
`main` の先頭でなければ何もせずに終わる。警告を出し、ジョブは成功で終える。
手動のロールバック（`workflow_dispatch`）は古いイメージに戻す操作なので、この確認をしない。

## 検討した代替案

### 案A: 承認する人が古い実行をキャンセルする

仕組みは変わらないが、今回の事故はまさに承認する側が古い実行と気づかずに承認して起きた。
人の注意に頼る運用は、同じ間違いをもう一度起こす。

### 案B: いま入っているイメージより古いコミットなら入れない

ECS のタスク定義からいまのタグを読み、git の履歴で前後を比べる。`main` の先頭のデプロイが
CI の失敗で作られなかったときも、その手前のコミットを入れられる。ただ、タグの読み出しと
履歴の取得（浅いクローンでは足りない）が要り、デプロイの手順が増える。`main` の CI が
失敗したら直して入れ直すのが普段の流れなので、先頭かどうかだけを見る方を選んだ。

### 案C: `concurrency` で古い実行をキャンセルする

`concurrency` が見るのは動いている実行と順番待ちの実行で、承認待ちの実行は対象にならない。
承認待ちの間に並んだ実行は、この設定では片付かない。

## 影響

- 承認待ちのデプロイが複数あるときは、`main` の先頭のものだけが入る。古い方を承認しても、
  警告を出して何もしない。
- `main` の先頭のコミットの CI が失敗すると、その手前のコミットのデプロイも入らなくなる。
  `main` を直したコミットのデプロイで入れる。手動のロールバックは ECR に入っているイメージにしか
  戻せないため、一度もデプロイしていないコミットには使えない。
- 承認から確認までの間に `main` が進むと、承認したデプロイは入らない。新しい方の承認を待つ。
- 見直す条件: `main` の CI の失敗で、入れたいデプロイが止まることが続いたら、案B に移る。
