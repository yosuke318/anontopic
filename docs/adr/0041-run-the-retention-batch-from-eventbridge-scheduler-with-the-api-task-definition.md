# ADR-0041: retention バッチを EventBridge Scheduler から API のタスク定義で動かす

- ステータス: Accepted
- 日付: 2026-10-27
- 関連 issue: YOSUKE-166

## 文脈

- retention バッチ（`cmd/retention`）は 1 日 1 回動かす（ADR-0026）。動かないと、14 日先の
  メッセージのパーティションが無くなって書き込めなくなり、90 日を過ぎた会話ログも消えない。
- サーバーは ECS Fargate で動き、デプロイはファミリーの最新のタスク定義のイメージだけを
  差し替えて新しいリビジョンを登録する（ADR-0034）。マイグレーションは、そのリビジョンで
  コマンドを `/migrate up` に替えたタスクを 1 回動かす。
- 失敗は `retention failed` のログと終了コード 1 で分かる。監視モジュールには、このログを
  見て通知する仕組みがある。
- 運用者はときどき確認するだけで、止まったことに自分で気づくのは遅れる。

## 決定

- リリースイメージに `retention` のバイナリを入れ、API と同じイメージから動かす。
- EventBridge Scheduler が毎日 05:00（日本時間）に ECS の `RunTask` を呼ぶ。タスク定義は API の
  ファミリーをリビジョンを指定せずに渡し、コマンドを `/retention` に替える。ECS はファミリーの
  最新のリビジョンを選ぶため、デプロイで入れたイメージで動く。
- `RunTask` はユニバーサルターゲット（`aws-sdk:ecs:runTask`）で呼ぶ。Scheduler のロールには、
  API のファミリーの `ecs:RunTask`（このクラスターに限る）と、実行ロールの `iam:PassRole` だけを許す。
- ログは API のロググループに出る。prod では次の 2 つで通知する。
  - `retention failed` が出たとき
  - `retention finished` が 24 時間出ないとき。タスクを起動できなかった、Scheduler が呼べなかった、
    途中で止まった、をまとめて拾う
- dev にも同じスケジュールを置く。dev は普段 destroy しているため、動くのは作っている間だけになる。

## 検討した代替案

### 案A: retention 用に別のタスク定義を作る

ログの置き場所は分けられるが、デプロイのたびにこのタスク定義のイメージも差し替える処理が要る。
差し替えを忘れると、古いイメージのまま新しいスキーマに対して動く。

### 案B: retention 用に別のイメージを作る

ビルドと ECR のリポジトリが増える。バイナリはサーバーと同じモジュールから作れ、イメージを
分ける理由が無い。

### 案C: テンプレートの ECS ターゲット（`ecs_parameters`）を使う

タスク定義の ARN を渡す形で、コマンドの差し替えを指定できない。

### 案D: API サーバーの中でタイマーを回す

2 タスクが同時に動くため、どちらか一方だけが走るよう排他が要る。デプロイの入れ替えの間に
重なったり、抜けたりもする。

### 案E: Scheduler の失敗を DLQ（SQS）で受ける

Scheduler が呼べなかったことしか分からず、タスクが起動後に止まった場合を拾えない。
`retention finished` が出ないことを見るほうが広く拾える。

## 影響

- Terraform でタスク定義を変えると、デプロイまでの間はファミリーの最新が `initial` のイメージを
  指す。その間の retention は古いイメージで動く。タスク定義を変えたら、続けてデプロイする。
- `retention finished` を見るアラームは、作った直後と、prod を立ててから最初の実行までの間は
  データが無いため鳴る。最初の実行が終われば戻る。
- API のロググループに retention のログが混ざる。ストリーム名はどちらも `api/api/<タスク ID>` で、
  `started-by` が `scheduler-retention` のタスクが retention になる。
- 見直す条件: retention の処理が 0.25 vCPU / 0.5 GB で足りなくなったら、案A のように
  タスク定義を分けて大きさを変える。
