# ADR-0048: トピック選択画面に、キューに待っている人がいるかどうかだけを出す

- ステータス: Accepted
- 日付: 2026-11-09
- 関連 issue: なし（トピックごとの賑わいを出す YOSUKE-219 とは別の判断）

## 文脈

- 利用者がトピックと人数を選ぶ前に、選んだらすぐ相手が見つかるのか、待つことになるのかを知りたい。
- キューには人が溜まらない。必要な人数が揃った時点で取り出されるため（ADR-0008）、
  2 人ルームのキューにいるのは多くても 1 人、3 人ルームでも 2 人まで。
  待っている人がいる 2 人ルームのキューを選べば、その場で会話が成立する。
- 人数を出すと、利用者が少ないうちは小さな数字が並ぶ。時間帯と合わせると特定の相手を
  待ち合わせる手がかりにもなる（設計書 3.2 の禁止行為に近づく）。
- トピック選択画面は、利用者がセッションを持つ前に開く画面。
- キューの状態は数秒で変わる。`/topics` はサーバーで描画するが、開いた時点の状態は
  すぐに古くなる。
- API サーバーは 2 台で、Redis は 1 ノード（ADR-0031）。

## 決定

matching モジュールに認証の要らない `GET /api/matching/queues` を足し、有効なトピックの
キュー（トピックとルーム種別の組）ごとに、待っている人がいるかを真偽値だけで返す。
答えは各サーバーのプロセス内で `MATCHING_STATUS_TTL`（既定 5 秒）使い回す。
画面はタブが表にある間、10 秒ごとに読み直し、待っている人がいるトピックと人数に
「待っている人あり」と出す。

## 検討した代替案

### 案A: 待っている人数をそのまま返す

キューに人が溜まらないので、ほとんどが 0 か 1 になり、真偽値以上のことは伝わらない。
小さな数字が並ぶ問題と、待ち合わせの手がかりになる問題がそのまま残る。

### 案B: `GET /api/topics` に待ちの有無を足し、サーバーでの描画時にだけ出す

ブラウザからの通信は増えないが、トピック一覧は 5 分キャッシュしている（ADR-0006）。
待ちの有無だけ別の TTL にしても、画面を開いた後の変化が出ない。数秒で変わる状態を
開いた時点で固定すると、「待っている人あり」を見て選んだのに待たされることが増える。

### 案C: 管理 API の `GET /api/admin/topics/presence` を公開する

人数（会話中と待機中）を返すため案A と同じ問題がある。管理用の API を
認証なしで公開することにもなる。

### 案D: キャッシュせず、要求のたびに Redis を読む

1 回は `ZCOUNT` をトピック数 × 2 個並べた pipeline 1 往復で軽い。ただ認証の要らない
エンドポイントなので、要求の数がそのまま Redis への往復になる。5 秒遅れても
困らない表示なので、要求の数に関係なく 1 台あたり 5 秒に 1 回に抑える方を選んだ。

## 影響

- 表示は最大で `MATCHING_STATUS_TTL` と画面の読み直し間隔を足した分（既定 15 秒）遅れる。
  2 台がそれぞれ答えを持つため、読み直すたびに表示が揺れることがある。
- 待機画面を閉じて `DELETE /api/matching` が呼ばれなかった利用者は、`MATCHING_WAIT_TTL`
  （既定 5 分）が切れるまで「待っている人」として数える。そのキューを選ぶと、
  もういない相手とルームが成立することがある。これはキューそのものの性質で、表示を足して
  起きやすくなったわけではない。待機画面が状態を問い合わせる間隔を寿命の目安にする
  仕組みを入れたら、表示も同じ寿命で絞れる。
- トピック選択画面を開いている利用者 1 人あたり、10 秒に 1 回の要求が増える。
  画面を開く人数が増えて API の負荷が目立つようになったら、間隔を延ばすか、
  答えを CDN で数秒キャッシュすることを検討する。
- 待っている人がいることは分かるため、待ち合わせの手がかりが全く無くなるわけではない。
  ただ、待ち合わせる 2 人は表示が無くても同じ時刻に同じトピックを選べば会えるので、
  表示を足すことで増える手がかりは小さいと判断した。
