# ADR-0007: 管理 API を環境変数の Bearer トークンで保護する

- ステータス: Accepted
- 日付: 2026-08-26
- 関連 issue: YOSUKE-122

## 文脈

トピックの追加・改名・公開停止は、選択画面に出る内容をそのまま変える操作なので、
誰でも叩ける状態で公開できない。一方で、判断の時点で次の事実がある。

- 管理者は開発者 1 名だけ。管理画面はまだ無く、当面は `curl` や社内からの手動操作で足りる。
- 利用者側は会員登録を持たない匿名セッション（ADR-0005）で、権限の概念がない。
  利用者のセッションをそのまま管理者判定に使うことはできない。
- 管理操作の頻度は月に数回程度。
- 予算・体制の制約から、ID プロバイダ（OIDC）の導入は現時点では割に合わない。

## 決定

管理エンドポイント（`/api/admin/topics`）は `ADMIN_API_TOKEN` に設定した秘密を
`Authorization: Bearer` で要求する。比較は定数時間で行う。

**`ADMIN_API_TOKEN` が未設定の環境では、管理エンドポイントを登録しない。**
設定を忘れた環境が、認証なしの書き込み口を晒すことがないようにする。

## 検討した代替案

### 案A: OIDC（Google など）で管理者を認証する

管理者 1 名・操作月数回に対して、クライアント登録・トークン検証・セッション管理の
実装と運用が重い。管理画面を作る段階で改めて選ぶ。

### 案B: ネットワークで閉じる（VPN / IP 制限）

インフラ側だけで守れるが、アプリ単体では無防備なままになり、ローカルや将来の
環境で経路の設定漏れがそのまま公開につながる。トークンと排他ではないため、
先にアプリ側で閉じておく。

### 案C: Basic 認証

保護の強さは実質同じで、利用者に見せる UI も無いのにブラウザの認証ダイアログを
前提にする形になる。API として使う分には Bearer の方が素直。

## 影響

- トークンは全管理者で共有される 1 個の値になり、誰が操作したかは記録できない。
  管理画面を作るときに、操作者を識別できる方式へ移行する必要がある。
- トークンの更新は環境変数の入れ替えと再起動になる。
- 管理画面を作る、または管理者が 2 名以上になった時点で ADR を書き直して supersede する。
