# ADR-0044: 性別と年代を任意で受け取り、マッチングには使わずに参加者の記録に残す

- ステータス: Accepted
- 日付: 2026-11-01
- 関連 issue: YOSUKE-159

## 文脈

- 設計書 3.1-1 と 3.2 は、性別・年齢による相手の指定や検索を機能として持たないことを求める
  （出会い系サイト規制法の対象にならないための線引き）。`/about` でも「属性で相手を指定する機能は持たない」と書いている。
- 利用者がどの層なのかが分からず、トピックの選び方や荒らしの傾向を考える材料が無い。
- 全年齢を対象にし、年齢確認は入れない（設計書 3.3）。未成年と申告した人への制限は、あとから別に考えたい。
- 参加者はセッショントークンだけで表す。識別子（`ip_hash`・`device_fingerprint`）は参加から 180 日で消し、
  通報された会話の参加者の分は残す（ADR-0037）。
- セッションは Redis にあり、マッチングは成立したときにセッションから識別子を読んで参加者の行に書く。

## 決定

- `/topics` で性別（女性・男性・その他）と年代（18 歳未満・18〜19 歳・20 代〜50 代・60 代以上）を任意で受け取る。
  どちらも「答えない」が既定。「マッチングには使わない」「相手には表示されない」を入力欄の横に書く。
- `POST /api/session` のボディで受け取ってセッションに持たせ、ルームが成立したときに `conversation_participants`
  の `gender` / `age_band` に書く。ボディを付けた要求は答えを置き換え、付けない要求は残す。
- matching モジュールは、受け取った属性を参加者の記録に渡すだけで、キューの選び方にも並び順にも使わない。
  キューのキーはトピックとルームの種類だけのまま。
- retention が参加から 180 日で識別子と一緒に消す。通報された会話の参加者の分は残す。
- プライバシーポリシーに、取得する情報・使う目的・保管する期間を足す。

## 検討した代替案

### 案A: 属性を受け取らない

設計書 3.1 / 3.2 とぶつかる心配は無い。ただ、利用者の層も、荒らしがどの層に偏るかも分からないまま運営することになる。
選別にも表示にも使わなければ「属性による相手の指定」にはならないので、受け取ったうえで使い道を絞る。

### 案B: 会話の相手に属性を表示する

相手の層が分かると安心する人はいる。ただ、表示すれば相手を見て抜ける・選ぶことができ、実質的に属性で相手を選ぶ機能になる。
3.1 / 3.2 の線を越えるので採らない。

### 案C: 年代ではなく年齢（数字）を受け取る

細かく集計できる。ただ、自己申告で精度は上がらず、識別に使える情報が増えるだけになる。18 歳を境に分けられれば足りる。

### 案D: セッションではなく `POST /api/matching` のボディで受け取る

経路は短い。ただ、待機に入るたびに送り直すことになり、マッチングの API に「マッチングには使わない値」が載って紛らわしい。
セッションに持たせれば、matching はセッションから識別子と一緒に読むだけで済む。

## 影響

- 性別か年代を答えた参加者は、識別子が消えたあとも 180 日までは属性で見分けやすくなる。
  消す対象を引くインデックスの条件に属性も足した。
- 未成年と申告した人への制限は入れていない。入れるときは、この決定を見直す ADR を書く。
- 見直す条件: 属性を表示したい・相手選びに使いたいという要望が出たら、3.1 / 3.2 の線引きから考え直す。
  集計に使っていないと分かったら、受け取るのをやめる。
