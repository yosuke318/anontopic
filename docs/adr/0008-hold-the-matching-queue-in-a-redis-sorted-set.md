# ADR-0008: マッチングキューを Redis の sorted set と Lua スクリプトで持つ

- ステータス: Accepted
- 日付: 2026-08-27
- 関連 issue: YOSUKE-123

## 文脈

待機キューをどこにどう置くかを決める必要がある。前提は次の 4 つ。

- API サーバーは固定 2 台構成（設計書 第5章）。どのサーバーに繋がった利用者も同じ待機列に入る。
- 1 人が 2 つのルームに割り当てられると、`conversation_participants` の行数を参加人数として
  数える前提（[ADR-0003](0003-one-row-per-conversation-participant.md)）が壊れる。
  同時実行下でも二重割当が起きないことは、issue の完了条件でもある。
- 待機時間そのものが判定材料になる。待機のタイムアウトと、3 人ルームの
  フォールバック（[ADR-0009](0009-fall-back-to-a-two-person-room.md)）は、
  どちらも「いつから待っているか」を見る。
- Redis はセッションの保管で既に使っている（[ADR-0005](0005-anonymous-session-tokens-in-redis.md)）。
  マッチングキューの置き場としても設計書 第3章が挙げている。

## 決定

キューを Redis の sorted set（member はセッショントークン、score は待機を始めた時刻の
ミリ秒）で持ち、ルームの取り出しを 1 本の Lua スクリプトで行う。スクリプトは
期限切れの削除・人数の判定・`ZPOPMIN` による取り出し・参加者ごとのキーの書き換えまでを
1 ステップで終える。

利用者の状態は 3 つのキーで表す。待機中は `matching:waiting:<token>`、成立したルームは
`matching:room:<token>`、キュー本体は `matching:queue:<topic_id>:<room_type>`。
状態の移動はすべてスクリプトの中で行うため、2 台のサーバーが同時に取り出しても、
同じトークンが両方のルームに入ることはない。

## 検討した代替案

### 案A: list（`LMPOP` / `RPOPLPUSH`）で持つ

到着順の取り出しは自然だが、要素に待機開始時刻を持てない。タイムアウトとフォールバックの
判定のために別のキーを引くことになり、取り出しの原子性がそこで崩れる。

### 案B: `WATCH` / `MULTI` による楽観ロック

競合時のリトライをアプリ側に書くことになる。参加が集中する時間帯ほど競合が増え、
リトライが最も必要な場面で最も失敗しやすい。Lua なら 1 往復で確定する。

### 案C: PostgreSQL の `SELECT ... FOR UPDATE SKIP LOCKED`

行ロックで同じ保証は得られる。ただし待機列は短命で更新が多く、90 日保持の会話ログと
同じインスタンスに書くことになる。待機のポーリングが接続数を食う点も、予算内の
インスタンス（設計書 第5章）と噛み合わない。

### 案D: サーバーのメモリに持つ

2 台のサーバーが別々の待機列を持つ。片方に 2 人、もう片方に 1 人という分かれ方をすると、
3 人が待っているのに 3 人ルームが成立しない。

## 影響

- スクリプトは `KEYS` に無いキー（取り出した参加者の `matching:waiting:` と
  `matching:room:`）を書く。取り出すまでキーが分からないためで、そのぶん
  Redis Cluster では動かない。単一ノード構成が前提になる。分割が必要になったら
  トピック単位でノードを分ける。
- 成立の通知は、参加者が `GET /api/matching` を呼んで受け取る。WebSocket の配送を
  実装したら push に移せる。
- ルームを取り出してから `conversations` を書くまでの間にサーバーが落ちると、
  参加者の `matching:room:<token>` が 30 秒で消えて待機前の状態に戻る。
  会話が二重にできるより、待機が一度無駄になる方を選んだ。
