# ADR-0031: RDS と ElastiCache を Single-AZ・1 台ずつで動かす

- ステータス: Accepted
- 日付: 2026-10-03
- 関連 issue: YOSUKE-137

## 文脈

- 設計書 5 章は PostgreSQL を「Multi-AZ、中型インスタンス（約 $70/月）」、Redis を
  「小型ノード 1〜2 台（約 $9〜20/月）」としている。Redis の Multi-AZ は決めていなかった。
- このサービスは個人の趣味で運営し、監視は運用者がときどき確認する程度にとどめる。
  停止時間やデータ消失に対して、利用者との約束（SLA）は無い。
- 月額予算は 4 万円前後で、設計書の見積もり（約 $280）でほぼ使い切っている。
- RDS の Multi-AZ はスタンバイの分だけインスタンス料金が 2 倍になる。ElastiCache の
  レプリカも 1 台分の料金がかかる。
- Redis には、セッション（ADR-0005）・マッチングキュー（ADR-0008）・接続のリース（ADR-0013）を
  置いている。Redis が止まると新しい接続を受けられない。ただしキューやセッションが消えても、
  利用者が入り直してマッチングし直せば元に戻る。

## 決定

- RDS PostgreSQL は Single-AZ のインスタンス 1 台で動かす。自動バックアップは残す
  （prod 7 日、dev 1 日）。
- ElastiCache Redis はレプリケーショングループを 1 ノードで作り、自動フェイルオーバーと
  Multi-AZ を無効にする。スナップショットは取らない。

## 検討した代替案

### 案A: 設計書どおり RDS だけ Multi-AZ にする

AZ やインスタンスの障害から 1〜2 分で戻れる。ただし月 $35 前後を、約束の無い可用性のために
払うことになる。インスタンスが止まっても、RDS が同じ AZ で立て直すか、バックアップから
戻せば足りる。

### 案B: RDS と Redis の両方を Multi-AZ にする

案A に加えて Redis のレプリカの分がかかる。しかも複製は非同期のため、フェイルオーバーの
直前に書いたキューやセッションは消えうる。利用者が入り直す必要があるのは、1 台構成で
立て直したときと変わらない。

### 案C: 自動バックアップも止める

バックアップのストレージは DB のサイズまで無料で、費用はほとんど減らない。消えても困らないと
しても、誤った destroy や操作ミスから戻す手段が無くなる。

## 影響

- AZ の障害やインスタンスの障害の間は、サービス全体が止まる。RDS は同じ AZ での立て直しか、
  別の AZ へのポイントインタイムリストアで戻す。後者は運用者が手で行い、エンドポイントが
  変わるため `DATABASE_URL` も入れ替える。
- Redis が立て直されると、全員のセッションとマッチングキューが消え、利用者は入り直しになる。
- ADR-0012 の文脈にある「RDS は Multi-AZ」は、この決定で Single-AZ になる。
  ADR-0012 の決定（書き込みをまとめる）はインスタンスの台数によらないため、変えない。
- 見直す条件: 利用者が増えて止まっている時間の影響が大きくなったとき、または予算に
  余裕ができたときは、RDS の `multi_az` から有効にする。Redis はノードを足して
  自動フェイルオーバーを有効にすれば、作り直さずに Multi-AZ にできる。
