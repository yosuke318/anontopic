# ADR-0026: 会話ログを日次パーティションごと 90 日で削除し、通報された会話は別テーブルに移して残す

- ステータス: Accepted
- 日付: 2026-09-27
- 関連 issue: YOSUKE-133

## 文脈

- 基本設計書 4.2 は `messages` を月次パーティションとし、90 日を超えたパーティションを
  `DROP TABLE` するバッチを深夜に流すとしている。初期マイグレーションも月次で作っている。
- LP と about ページは利用者に「会話ログは 90 日で自動的に削除します」と約束している。
- ストレージの見積もりは 90 日分で約 240GB（設計書 5 章）。1 日あたり約 2.7GB になる。
- パーティションは丸ごと消える。通報された会話（ADR-0021 で `is_flagged` を立てたもの）は
  保持期間を過ぎても残す必要があり、設計書は「別テーブルへ退避、または保持期間を 1 年に延長」と
  方式を未決にしている。
- `messages` への書き込みは `chat` が持つ（ADR-0010）。設計書 1.3 は、`retention` が
  `report` に「フラグ付き会話か」を問い合わせてから削除対象を決めるとしている。
- API サーバーは冗長化のため 2 台で動かす（設計書 5 章）。

## 決定

- `messages` を **UTC の 0 時で区切る日次パーティション**にし、範囲の終わりが 90 日より前に
  なったパーティションを `DROP TABLE` する。行の入っている既存の月次パーティションは、
  期限が来るまでそのまま使う。
- パーティションを消す前に、そのパーティションに発言のある会話のうち `reports` に行がある
  会話のメッセージを `retained_messages` に移す。移動と `DROP` は 1 トランザクションで行う。
  `retained_messages` は自動では削除しない。
- 通報されたかどうかは `report` が `reports` から答える。`chat` の `is_flagged` は見ない。
- バッチは独立したコマンド `cmd/retention` とし、スケジューラから 1 日 1 回起動する。
  今日から 14 日先までのパーティションを作ってから、期限切れを削除する。`-dry-run` で
  予定だけを出す。失敗は `retention failed` のログと終了コード 1 で知らせる。
- `retained_messages` の書き込みと、`Transcript` での読み出しは `chat` が持つ。
  ADR-0010 の表に `retained_messages` の INSERT を `chat` の担当として足す。

## 検討した代替案

### 案A: 設計書どおり月次パーティションで、範囲の終わりが 90 日を過ぎたら削除する

1 か月分が丸ごと期限を過ぎるまで消せないため、実際の保持は 90〜121 日になり、利用者への
約束を破る。ピークの容量も 240GB × 121/90 ≈ 320GB になり見積もりを超える。
範囲の始まりで切れば 90 日は守れるが、60 日で消える会話が出る。

### 案B: 通報された会話を含むパーティションを 1 年残す

通報は日常的に起きるので、ほぼすべてのパーティションが 1 年残り、容量が頭打ちにならない。
通報されていない会話まで 90 日を超えて残り、約束も破る。

### 案C: パーティションは使わず、期限切れの行を `DELETE` する

通報された会話を条件で除けるので退避が要らない。ただし 1 日約 2.7GB を毎晩 `DELETE` すると、
不要領域の回収を VACUUM に頼ることになり、容量がすぐには戻らず書き込みの負荷も重なる。

### 案D: `conversations.is_flagged` を `chat` の中で見て除外する

問い合わせが 1 段減る。ただし設計書 1.3 に反し、通報の記録を持つ `report` を通らない。
`reports` への記録後に `is_flagged` の更新だけ失敗した会話（ADR-0021 ではクライアントの
再送で完了する）を取りこぼすが、`reports` を見ればその会話も残る。

### 案E: API サーバーの中で定期実行する

2 台で同時に走るため排他が要る。成否がサーバーのログに埋もれ、プロセスの終了コードで
失敗を知らせられない。

## 影響

- 容量は「91 日分 + `retained_messages` + 今日から 14 日先の空パーティション」で頭打ちになる。
  見積もりどおりなら約 243GB。`retention finished` のログに残りのパーティション数と
  合計サイズを出すので、実測で確かめられる。
- 生きているパーティションは常時 100 個強になる。範囲で絞れない問い合わせ（会話 ID だけで
  引く `Transcript` など）は全パーティションの索引を順に見る。
- バッチが 14 日続けて失敗すると、その先のメッセージは記録できなくなる。
  アラートを張るまでは、この 14 日が気づくまでの猶予になる。
- パーティションの `DROP` は `messages` 全体をロックする。長い問い合わせに待たされて書き込みが
  詰まらないよう、ロック待ちは 5 秒で諦め、翌晩に持ち越す。
- `retained_messages` は通報された会話の分だけ増え続ける。法務上の保存期間が決まったら
  期限を設ける。
- `conversations` と `conversation_participants` の行はこのバッチでは消えない。参加者の
  IP 関連項目の保持期間（設計書 4.2）と、終了が記録されなかった会話の片付け（ADR-0010）は別に扱う。
- 設計書 4.2 の「月次パーティション」からの逸脱にあたる。設計書を更新する場合はこの ADR を根拠にする。
- 見直す条件: パーティション数が問い合わせの計画時間に効いてきたら、週次への変更を検討する。
