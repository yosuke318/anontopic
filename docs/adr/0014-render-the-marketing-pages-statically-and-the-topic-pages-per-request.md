# ADR-0014: LP と紹介ページは静的に生成し、トピック選択と待機はリクエストごとに描画する

- ステータス: Accepted
- 日付: 2026-09-05
- 関連 issue: YOSUKE-127

## 文脈

フロントエンドは Next.js の App Router で、LP・紹介ページは SSR/SSG、チャット画面は CSR と
決まっている（設計書 8）。収益は Google AdSense を前提にしているため（設計書 5）、
検索から入ってくるページの初期表示と SEO が売上に直結する。ここで決めるのは、
チャット画面より手前にある LP・紹介ページ・トピック選択画面・待機画面の描画方法になる。

- LP と紹介ページの内容はコードの中にあり、API も DB も読まない。
- トピック一覧は管理 API から変更でき、API サーバーはプロセス内に既定 5 分キャッシュする
  （[ADR-0006](0006-cache-the-topic-list-in-process.md)）。反映の遅れはこの 5 分が上限で、
  フロントエンド側でさらに保持すると遅れが積み上がる。
- 待機の状態はセッションごとに違い、成立の判定は `GET /api/matching` の呼び出しが兼ねている。
  静的に持てるものが無い。
- `make check` と CI は API サーバーもデータベースも起動していない状態で走る。ビルドが
  API への到達を必要とすると、フロントエンドの検査がバックエンドの起動に依存する。
- Next.js のサーバーとブラウザでは API のホスト名が異なる。compose ではサーバーが
  `api:8080`、ブラウザが `localhost:8080` を見る。

## 決定

経路ごとに描画方法を分ける。

- `/`（LP）と `/about`（紹介）はビルド時に静的生成する。データ取得を持たせない。
- `/topics`（トピック選択）と `/waiting`（待機）は `dynamic = "force-dynamic"` を付け、
  リクエストごとにサーバーで描画する。トピック一覧は `cache: "no-store"` で毎回 API から読む。
- トピック一覧の取得は `<Suspense>` の内側に置き、見出しと説明の部分を先に返す。
- クライアント側に置くのは、キューへの参加と待機状態のポーリングだけとする。ブラウザから
  API を呼ぶ経路には Cookie が必要なため、`credentials: "include"` を付ける。
- サーバー側が使う API のオリジンは `API_BASE_URL`、ブラウザに配る値は
  `NEXT_PUBLIC_API_BASE_URL` として別々に持つ。
- `sitemap.xml` と `robots.txt` は静的に生成し、`/waiting` はクロール対象から外す。

## 検討した代替案

### 案A: トピック選択画面も静的に生成し、ブラウザからトピックを取りに行く

LP と同じく CDN に載せられる。ただしトピックが出るまでに 1 往復かかり、その間は
選択肢が無い画面になる。検索エンジンが見る HTML にもトピックが載らない。
選択肢の一覧はこの画面の中身そのものなので、サーバーで埋めて返す。

### 案B: トピック選択画面を ISR（`revalidate`）で持つ

配信は速くなる。ただしビルド時に一度 API を叩くため、API が起動していない環境で
ビルドが失敗する。CI とローカルの `make check` がバックエンドの起動に依存することになる。
加えて API 側が 5 分キャッシュを持っているため、そこにフロントエンドの保持時間が
上乗せされ、管理 API での変更が反映されるまでの時間が読みにくくなる。

### 案C: 4 画面すべてを Client Component にする

チャット画面と同じ作りにできる。ただし LP と紹介ページの本文が初期 HTML から消えるため、
SEO と AdSense の審査という目的に正面から反する。

## 影響

- API が応答しないと `/topics` はトピックを出せない。画面は落とさず、読み込み直す導線を
  持つ notice に差し替える。`/waiting` はトピック名の表示だけを諦めて待機を続ける。
- `/topics` と `/waiting` はリクエストごとに Next.js のサーバーを通る。CDN で吸収できるのは
  LP と紹介ページだけになる。トピック選択の負荷は API 側のキャッシュで受ける。
- 待機中のクライアントは 2 秒ごとに `GET /api/matching` を呼ぶ。同時待機者が増えると
  この呼び出しがそのまま比例して増える。
- Next.js のサーバーが API に到達できる位置に必要になる。ホスティングを決める段で、
  `API_BASE_URL` が指せる経路があることを前提にする。
- 見直す条件: 待機のポーリングが API の負荷として無視できなくなったら、WebSocket や
  Server-Sent Events で成立を通知する方式に変える。
