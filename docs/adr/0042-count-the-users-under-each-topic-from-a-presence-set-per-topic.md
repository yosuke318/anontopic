# ADR-0042: トピックごとの人数を、トピック単位の接続の記録から数える

- ステータス: Accepted
- 日付: 2026-10-28
- 関連 issue: YOSUKE-229

## 文脈

- 運用者が管理画面（anontopic-admin）で、各トピックにいま何人いるかを 5 秒ごとに見たい。
- 管理画面は本体の管理 API（`/api/admin/*`）だけを呼ぶ。本体の PostgreSQL や Redis には直接つながない。
- 会話に接続している参加者は、会話ごとの sorted set（`chat:presence:{conversationID}`）で
  Redis に記録している。キーにはトピックが入っていないため、トピックごとの数はそのままでは引けない。
- 待機中の利用者は、トピックと部屋の種類ごとの sorted set（`matching:queue:{topicID}:{roomType}`）にいる。
- Redis は 1 ノード構成（ADR-0031）。
- 管理画面はローカルで 1 人の運用者が開くだけで、同時に開くのは多くても数枚。

## 決定

chat モジュールが、会話ごとの記録と同じスクリプトの中で、トピックごとの sorted set
（`chat:topic-presence:{topicID}`、メンバーは `{conversationID}:{token}`、スコアは最後に接続を記録した時刻）
にも書く。`GET /api/admin/topics/presence` は、この set と待機キューを `ZCOUNT` で数えて返す。
管理画面はこの API を 5 秒ごとに呼び直す。

## 検討した代替案

### 案A: `chat:presence:*` を SCAN して、会話からトピックを PostgreSQL で引く

書き込みは増えない。ただ、呼ぶたびに Redis のキー空間を全部なめて、さらに進行中の会話を
DB から読むことになる。5 秒ごとに呼ぶ API としては重く、数が会話の数に比例して増える。

### 案B: PostgreSQL の進行中の会話（`ended_at` が NULL）から参加者を数える

会話が成立した時点の参加者の数で、いま接続しているかどうかは分からない。再接続の猶予
（ADR-0011）の間は、切れた参加者も数に入ってしまう。

### 案C: 本体から管理画面へ人数の変化を送り続ける（SSE や WebSocket）

人数が変わった瞬間に画面に出る。ただ、管理画面はブラウザにトークンを渡さない作り
（Rails のサーバーだけが API を呼ぶ）なので、本体 → Rails → ブラウザの 2 段の中継が必要になる。
ローカルで 1 人が眺める画面に対して仕組みが大きすぎ、5 秒遅れで困る用途でもない。

## 影響

- 接続を記録するたびに、Redis への書き込みが会話のキーとトピックのキーの 2 つになる。
  1 つのスクリプトにまとめているので往復の回数は変わらない。
- スクリプトが 2 つのキーを書くため、Redis Cluster に移るときはハッシュタグなどで
  同じスロットに置く必要がある。
- 接続を持つサーバーが落ちると、その参加者は接続の記録の寿命（`PresenceTTL`、既定 30 秒）が
  切れるまで数に残る。
- 管理画面を開いている間、5 秒ごとにトピックの一覧（PostgreSQL）と Redis への pipeline が 1 回ずつ走る。
  運用者が増えて画面を開く数が増えたら、本体側で数えた結果を短くキャッシュすることを検討する。
